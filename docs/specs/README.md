# agent_project 规格驱动开发规范(SDD·轻量版)

> **本目录是系统所有"应有行为"的契约库 —— 单一事实来源(SSOT)。**
> 开发模式:AI-native(agent 实现全部代码,人负责需求与验收,事后读代码/文档学习)。
> spec 是 agent 的**方向盘**(实现前固定"做什么/做到什么程度")和**跨会话记忆**(防二次实现)。
> 行为门禁见仓库根 `CLAUDE.md`「开发流程(SDD)」;本文件是 spec 体系的操作手册。

---

## 1. spec 是什么(核心理念)

spec 不是"流程文档",是**系统应有行为的事实来源**。

**法律类比**(理解的关键):
- spec = 法律(定义系统**该怎样**,稳定)
- 代码 = 人的行为(可能偏离法律)
- **bug = 行为偏离法律** → **改代码回归,法律(spec)不动**
- **法律本身有漏洞** = spec 错了/漏了 → **才修法(改 spec)**

多数 bug fix 不改 spec(契约对,代码错);只有契约本身漏了/错了,才更新/新建 spec。

## 2. 为什么需要 spec(AI-native 模式的两个理由)

1. **输出质量由指令质量决定**:agent 实现,spec 是它唯一的需求输入。spec 清晰 → 实现不跑偏;没 spec → 每次会话从对话上下文猜需求。
2. **跨会话记忆**:不同会话的 agent 不记得以前做过什么。每个功能有契约 spec 后,动手前 `grep docs/specs/` 就能发现"这功能已定义过",不会二次实现/覆盖。

## 3. spec 的分级(都写,但深度按影响面)

| 类型 | 影响面 | 模板深度 | 例子 |
|------|--------|----------|------|
| **功能**(新) | 完整 | 完整(背景/MoSCoW/G-W-T/模块) | 混合检索、Agent 循环 |
| **修复** | 轻量 | 精简(背景一句/验收G-W-T/涉及模块) | 修某个解析 bug |
| **重构** | 完整 | 完整模板 | 换向量库后端 |
| **回溯契约** | 完整 | 完整模板(标"类型:回溯") | 给已存在功能补契约(见 §8) |

**可不写 spec**(零行为变化的改动):注释 / 纯文档 / 依赖升级 / README 更新。

## 4. 防二次实现门禁(核心机制)

**动手前必做:`grep -ri <关键词> docs/specs/` 查相关契约。**

- 查到相关契约 spec → **更新它**(加修订记录,见 §7),不新建
- 查不到 → 新建 `SPEC-NNN`

**关键词举例**:改检索 → `grep -ri "检索\|search\|rerank" docs/specs/`;改分块 → `grep -ri "分块\|chunk" docs/specs/`。

## 5. 闭环七步(核心流程)

```
0. grep 防重     → grep docs/specs/ 查相关契约                  [查到→更新; 无→新建]
1. 写 spec       → docs/specs/SPEC-NNN-短名.md                  [📝 草稿]
2. 人确认方案     → spec 改 ✅已确认                              [✅ 已确认] ← 门禁通过
3. 实现 + 写测试  → src/ 下写代码 + tests/ 下写验收脚本          [🔨 进行中]
4. 逐条验收       → 验收脚本跑通 + AC 核对
5. 同步收尾       → 以下六件事同一次提交完成(见下方清单)
6. git commit    → Conventional Commits 格式提交
```

**步骤5 同步收尾清单(每次必做,缺一不可):**

| 序号 | 产物 | 位置 | 做什么 |
|------|------|------|--------|
| a | spec 本身 | `docs/specs/SPEC-NNN.md` | 状态改 ✔已验收,逐条勾 AC,回填实现备注(踩坑/实测数据) |
| b | 回溯清单 | `docs/specs/README.md` §8 | 如适用,更新回溯清单 |
| c | 架构详解(新模块) | `docs/架构详解/0X-模块名.md` | 新模块必须新增详解;已有模块有重大变更时追加节 |
| d | 总览与导读 | `docs/架构详解/00-总览与导读.md` | 模块表 + 阅读路线 + 业界对比表同步 |
| e | 项目入口 | `learning/agent_project/README.md` | 文档索引 + 路线图 + 踩坑速查同步 |
| f | 宪法 | 仓库根 `CLAUDE.md` | 项目结构树同步(如有目录新增/移动) |

**门禁(铁律)**: spec status ≠ ✅已确认 时,严禁改核心代码(`src/agent_project/` 下各模块)。

**诚实验收(铁律)**: 验收脚本跑不通 / AC 未逐条核对 / 有跳过的步骤,不得宣称完成,必须如实报告。

**反例(踩坑教训):** 只改了 spec 和代码,漏了 00-总览和 README → 新模块在文档里查不到。

## 6. 验收标准怎么写(Given-When-Then)

格式: `Given <前置条件> When <动作/事件> Then <可观测结果>`

**正例**(取自本项目的检索契约 SPEC-001):

```
AC1 - 粗排检索:
  Given 已有某 PDF 的 .index 与 .json 产物
  When search(问题, index, meta, k=20)
  Then 返回 20 条,按余弦相似度降序,每条含 chunk/meta/score

AC4 - 嵌入前缀约定(BGE 非对称约定):
  When 建库 embed_texts() 与查询 embed_query() 分别编码
  Then passage 不加前缀;query 自动加"为这个句子生成表示以用于检索相关文章:"
```

**反例**:
- ❌ "检索应该更准"(不可观测)
- ✅ "问题 X 的精排 top-3 中,块 92(Preferences)进入 top-3 而粗排中它在第 8 名之后"(可观测)

验收脚本原则上放 `tests/`(可重复跑,长期保留);一次性探索脚本可临时放仓库根 `temp/`(不入库,验收结论要固化进 spec 或 tests)。

## 7. 修订已有 spec 的规则(不覆盖,留痕)

- **小修订**:原 spec 末尾加「修订记录」→ `YYYY-MM-DD 修订: <改了什么>(原因: <...>, 见 SPEC-NNN)`
- **大变更**(行为本质改了):新建 `SPEC-NNN`,开头注明取代关系;旧 spec 状态改 🗑已废弃 + 指向新 spec(文件保留不删)

## 8. 回溯清单(给已存在功能补契约)

渐进式:碰到哪个模块改动,顺手补契约;优先"将来最可能再改"的行为。

- [x] **SPEC-001 检索两段式契约**(search 粗排 + rerank 精排 + 前缀约定)— 回溯示范
- [ ] 分块契约(chunk_size/overlap/分隔符优先级)
- [ ] 文档解析契约(文本层判定阈值/OCR 降级)
- [ ] 建库契约(FAISS + JSON 双产物/id 对应/ASCII 文件名)
- [ ] 生成契约(prompt 模板约束/temperature/薄抽象换供应商)

## 9. 文件命名与状态

- **命名**: `SPEC-NNN-短slug.md`,NNN 递增,不回收
- **状态**(文件顶部): 📝草稿 → ✅已确认 → 🔨进行中 → ✔已验收(归档保留) / 🗑已废弃

## 10. 与其它文档的职责分工(勿混)

| 文档 | 职责 | 时态 |
|------|------|------|
| **docs/specs/SPEC-NNN** | 功能的**应有行为契约** | 应然(该怎样) |
| **docs/架构详解/** | 已完成功能**怎么实现的、机制原理**(学习文档) | 实然(怎么实现) |
| **README.md** | 项目入口:概览/索引/运行/路线图 | 现在 |
| **CLAUDE.md(仓库根)** | AI 行为宪法(环境/依赖铁律 + SDD 门禁) | 常驻 |
| **temp/ 验证脚本** | 一次性探索(不入库;结论固化进 spec 或 tests) | 临时 |

一句话: **spec 管"该怎样",README 管"怎么实现的",CLAUDE.md 管"怎么干活"。各管一段,不互相替代。**

## 11. 给 AI 的硬约束

1. 接到任何行为改动需求(含 bug fix),先 `grep -ri <关键词> docs/specs/`;查到→更新,查不到→新建。
2. spec status ≠ ✅已确认 时,拒绝改 `src/agent_project/` 核心代码。
3. 实现完,spec 状态改 ✔已验收 + 勾掉 AC + 必要时同步对应模块的架构详解。
4. AC 用 Given-When-Then 写,可观测、可验收。
5. 修订 spec 不覆盖核心定义,加修订记录或新建引用。
6. 实现中发现方案有问题,先改 spec 再改代码,不"代码先行、spec 事后补"。
7. 失败时不宣称完成:验收跑不通/步骤跳过,如实报告。
