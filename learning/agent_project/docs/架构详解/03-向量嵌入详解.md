# 03 · 向量嵌入(embedder)

> 解决的问题:把文本变成**可计算的语义表示**(512 维向量),
> 让"意思相近"变成"距离相近",检索才能用数学做。

## 1. 什么是嵌入(bare 机制)

嵌入模型把一段文本映射成一个固定长度的向量(本项目 BGE bge-small-zh-v1.5 → 512 维):

```
"Wireshark 解密 HTTPS"   → [0.025, 0.031, 0.058, ..., -0.024]  (512 个数)
"HTTPS 流量怎么还原明文" → [0.031, 0.028, 0.049, ..., -0.019]  (和上面很接近)
"Wireshark 界面主题设置" → [-0.012, 0.044, 0.003, ..., 0.037]  (和上面较远)
```

训练目标就是"语义相近的文本 → 向量夹角小"。之后"找相关文档" =
"找夹角最小的向量"——纯数学,毫秒级。

## 2. 双塔模型(bi-encoder)与非对称约定

**双塔**:query 和 passage **各自独立**过同一个模型,各自出向量,再算余弦。
"双塔"= 两边各一座编码塔,互不相见。好处:passage 向量可**离线预计算**,
检索时只算一次 query。代价:两塔无交互,精度有上限(详见《05-重排序》的对照)。

**BGE 的非对称前缀约定**(本项目最容易踩的认知坑):

```python
_QUERY_INSTRUCTION = "为这个句子生成表示以用于检索相关文章:"

embed_texts(texts)          # passage(文档块):不加前缀  ← 建库用
embed_query(query)          # query(用户提问):自动加前缀 ← 检索用
```

为什么:BGE 是**非对称**检索模型(s2p:短问题 → 长文章),训练时 query 带这句指令。
不加前缀的 query 和 passage 不在同一个对齐过的语义空间,余弦相似度失真、检索质量下降。
这是模型卡官方要求,不是可选优化。**所以 encoder 对外暴露两个语义化函数,
把约定固化在接口里,调用方想错都难。**

## 3. L2 归一化 → 内积即余弦

```python
model.encode(texts, normalize_embeddings=True)   # 每个向量长度 = 1
```

向量长度归一后,**内积 = 余弦相似度**,值域 [-1, 1]。
这决定了《04》里 FAISS 用 `IndexFlatIP`(内积索引)就能做余弦检索。

## 4. 模型加载:本地快照直载(含全部踩坑)

这是本项目踩坑最密集的地方,完整记录:

### HuggingFace 缓存结构(裸机制)

```
S:\huggingface_cache\
└── models--BAAI--bge-small-zh-v1.5\
    ├── blobs\        ← 实际文件内容(按哈希命名)
    ├── refs\         ← 版本指针
    └── snapshots\    ← "模型本体"目录(指向 blobs 的引用)
        └── 7999e1d3...\
            ├── config.json / model.safetensors / tokenizer.json ...
```

`snapshots/<hash>/` 就是模型本体——**把模型当成"本地一个文件夹"来理解**。

### 最终方案:直接解析快照路径喂给模型

```python
def _resolve_model_path() -> str:
    base = Path(r"S:\huggingface_cache\models--BAAI--bge-small-zh-v1.5\snapshots")
    if base.exists():
        snaps = sorted(base.iterdir())
        if snaps:
            return str(snaps[0])      # 本地目录路径
    return "BAAI/bge-small-zh-v1.5"   # 无缓存时退回 repo-id(需联网)
```

`SentenceTransformer(本地目录路径)` 时库发现是路径,**不走任何 hub 逻辑**,
任何版本都不联网——对库版本行为差异彻底免疫。

### 踩坑全记录(按时间线)

| 坑 | 现象 | 根因 | 解法 |
|----|------|------|------|
| 联网检查崩溃 | 启动时 HEAD huggingface.co 超时/连接重置(10054),重试后 `client has been closed` 崩溃 | 新版 sentence-transformers 启动时检查模型更新,国内网络不通 | 见下一行 |

| 版本大跳 | 行为和之前不一样、一堆新警告 | conda 安装 openai 时连带把 sentence-transformers 升到 5.6.1、transformers 5.14.1、huggingface_hub 1.24.0 | 装"小"包也可能动全家桶,升级后要回归验证 |

而是**给库一个本地路径**,让它根本不需要网络。

## 5. 业界选型与取舍

### 选型一:嵌入模型

| 候选 | 特点 | 劣势(对本场景) |
|------|------|------|
| **BGE bge-small-zh-v1.5(本项目)** | 中文强、100MB、本地离线免费、512 维 | 单语种(中) |
| BGE bge-large-zh / bge-m3 | 效果更好 / 多语言 | 体积与速度 ×3~5,单文档中文场景收益小 |
| M3E / text2vec | 中文可用 | C-MTEB 榜不如 BGE 系 |
| OpenAI text-embedding-3 | 效果强、省心 | 付费 + 数据外发 + 依赖网络,与"本地离线"冲突 |

**本项目的取舍逻辑**:标准按优先级 ①本地离线免费 ②中文效果 ③资源占用
(8G 显存的笔记本)④单文档量级下精度足够。small 档全占。**升级触发条件**:
多语言文档或大规模语料(效果差距会被放大)。

### 选型二:模型加载方式

| 候选 | 思路 | 问题 |
|------|------|------|
| 环境变量开关(HF_HUB_OFFLINE 等) | 拦住库的联网行为 | 开关分多层、随版本变,踩过坑 |
| **本地快照路径直载(本项目)** | 给库一个目录,它就不需要网络 | 路径硬编码(用 `_resolve_model_path` 兜住) |
| python-dotenv / 自动下载 | 省事 | 不解决联网问题;多一个依赖 |

**取舍逻辑**:稳定性 > 简洁性。联网类问题最稳的解法不是"拦请求"(面多、层多、
版本行为漂移),而是"让库根本不需要网络"。

## 6. 接口契约

```
embed_texts(texts: list[str]) -> list[list[float]]    # passage,不加前缀,建库用
embed_query(query: str | list[str]) -> list[list[float]]  # query,自动加前缀,检索用
```

两个函数底层共享 `_encode`(干活只此一份),差异仅在前缀开关。
产出向量列表交给《04-向量检索》入 FAISS 库。

### Q1 · 什么是嵌入?用自己的话说清"语义相近 = 距离近"是怎么来的。
**难度: 基础** · 考点: 概念本体

> **你的回答**:
> 嵌入是将文本块按一定的格式统一嵌入一个固定的空间中，通过归一化后的嵌入是可以嵌入到同一个三维球体中，语义相近的通过相同算法得到的空间坐标也相近，所以在这个空间中找文本块的时候距离近。

> [!tip] 批改 · 7/10
> ✅ "语义相近 → 坐标相近"核心直觉正确；提到归一化和球体是加分。
> ❌ **"关键词匹配不好"是结论不是原因**——应该说清"为什么不好"：关键词是**字面匹配**，搜"HTTPS 加密"找不到"TLS 握手协议"。
> ❌ **没提向量搜索的核心机制**：向量化后用余弦相似度，语义相近的句子向量距离近，不管措辞怎么变。
> ❌ "三维球体"表述不准确——BGE 输出 768 维，是 768 维超球面，不是三维。
>
> **改进版**：
> 嵌入是把句子映射到 768 维语义空间，语义相近的句子在空间中距离近。训练时让"意思一样"的句子对距离拉近、"意思不同"的推远，所以学完之后"语义相近 = 距离近"。检索时用户问题嵌入成一个向量，在知识库所有向量中找最近的——核心区别：关键词是"字一样才算匹配"，向量是"意思一样就算匹配"。

### Q2 · BGE 的前缀约定是什么?passage 和 query 分别加不加?不加前缀会发生什么?为什么?
**难度: 机制** · 考点: 非对称模型(本题是本篇最重要的一题,也是最容易漏的坑)

> **你的回答**:
> BGE前缀约定用来区分问题和内容，进入不同的编码塔，query加，passage不加，不加前缀的话问题会被编码进内容的塔里，而且如果问题太短的话没有前缀会最编码产生很大影响。

> [!tip] 批改 · 6/10
> ✅ query 加、passage 不加——规则答对了。"问题太短会受影响"直觉对。
> ❌ **"不同的编码塔"不准确**：BGE 不是双塔模型（双塔是 05 讨论的），BGE 是**单塔非对称**——同一个模型，靠前缀开关切换行为模式，不是两个塔。
> ❌ **没解释"不加前缀会怎样"的具体后果**：不加前缀 → query 被当 passage 编码 → 语义空间不对齐 → 检索召回率大幅下降。
> ❌ "问题太短"应该是"问题太短**且没前缀**"——短 query 没有足够语义信息，前缀是唯一的上下文补充。
>
> **改进版**：
> 前缀约定区分 query 和 passage 的编码模式：query 加"[query]: "，passage 不加。BGE 是单塔非对称——同一个模型，靠前缀开关切换行为模式。不加前缀 → query 被当 passage 编码 → 语义空间不对齐 → 召回率大幅下降。短 query 尤其依赖前缀，因为 query 本身语义信息少，前缀是唯一的上下文补充。

### Q3 · 为什么 L2 归一化之后内积就等于余弦?如果不归一化,对下游 FAISS 的选择有什么影响?
**难度: 机制** · 考点: 数学基础

> **你的回答**:
> 因为归一化后向量的模等于1，所以内积等于余弦，如果不归一化，不同向量的值除了方向外，模的大小也会对向量计算产生影响，这个影响对我们无用，无关变量应该排除

> [!tip] 批改 · 8/10
> ✅ "归一化后模=1 → 内积=余弦"正确；"模的大小对计算产生影响"正确；"无关变量应排除"是好的工程直觉。本篇最佳答案。
> ❌ **没提 FAISS 选型影响**：不归一化 → 必须用 IP（内积）索引且结果受模长污染 → 召回不准；归一化后 → 可以用更高效的 L2 索引（归一化后 L2 距离与余弦等价），或者直接用 IP 索引结果就是余弦。
>
> **改进版**：
> 归一化后 ||a||=||b||=1，内积 a·b = cos(θ)。如果不归一化，模长大的向量内积天然大（即使方向不同），模长成为噪音。对 FAISS 的影响：归一化后 L2 距离与余弦等价（L2² = 2 - 2cosθ），可以用更快的 L2 索引；未归一化只能用 IP 索引且结果受模长污染。

### Q4 · 双塔模型为什么快?这个快是用什么代价换的?两塔之间交换信息吗?
**难度: 决策** · 考点: 速度/精度取舍

> **你的回答**:
> 双塔模型对问题进行分离了，问题和资料是不同的编码塔，所以可以预先存数据的向量，只需要转化问题为query向量就好，所以双塔模型快，这种双塔模型没有信息交换，所以检索精度会稍微下降。

> [!tip] 批改 · 6/10
> ✅ "预存向量 + 只编码 query"正确；"没有信息交换 → 精度下降"正确。
> ❌ **"不同的编码塔"表述不够准确**：双塔是**两个独立编码器**（各一个 Transformer），不是"不同的编码塔"。
> ❌ **没回答"快是用什么代价换的"的具体含义**：代价是 query 和 document 在编码时完全独立，无法做细粒度交互（比如"这个 document 的第 3 段正好回答了 query"），所以精度比交叉编码器（cross-encoder）低。
> ❌ **没提 cross-encoder 对比**：双塔是"先编码再比对"（快但粗），交叉编码器是"一起编码"（慢但准）——这就是为什么需要 reranker（05）。
>
> **改进版**：
> 双塔 = 两个独立编码器（query 一个、document 一个），各自独立编码后只做向量比对（余弦相似度）。快的原因：文档向量预计算存好，查询时只编码 query 一次。代价：query 和 document 编码时完全独立，无法做细粒度交互（比如"这个段落正好回答了那个问题"），所以精度比交叉编码器（cross-encoder，把 query+doc 拼一起编码）低。这就是为什么需要 05-reranker 做二次精排。
