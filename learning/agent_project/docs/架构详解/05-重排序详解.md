# 05 · 重排序(reranker:粗排之后的精排)

> 解决的问题:双塔粗排"快而粗",会把语义相关但字面不贴近的块排到后面。
> 交叉编码器**慢而准**,对粗排召回的候选逐一精算,把真正相关的块提上来。

## 1. 核心机制:交叉编码器(cross-encoder)vs 双塔(bi-encoder)

| | 双塔(bi-encoder,《03》嵌入模型) | 交叉编码器(cross-encoder,本模块) |
|---|---|---|
| 输入方式 | query、passage **各自**编码成向量 | query 和 passage **拼成一条**输入 |
| 交互 | 无——两塔各自"总结",总结完才比对 | **逐 token 交叉注意**:query 的每个词和 passage 的每个词直接交互 |
| 输出 | 两个向量,再算余弦 | 一个相关性分数(logit) |
| 速度 | 极快:passage 向量可**离线预计算**,检索=一次矩阵乘 | 慢:N 个候选 = N 次完整前向,**无法预计算** |
| 精度 | 有上限(信息在各自编码时已压缩) | 显著更高(细粒度交互) |

**一句话**:双塔像"两人各写摘要再比对摘要",交叉编码器像"两人面对面逐句核对"。

## 2. 两段式设计:经济学的必然

```
313 个块 ──双塔粗排──→ top-20 候选 ──交叉编码器精排──→ top-3 喂 LLM
           (毫秒)                                    (20 次前向,秒级内)
```

- 全库 313 块都跑交叉编码器?太慢(几百次前向)
- 只用双塔取 top-3?够快但排序粗糙
- **粗排保证"相关的都在前 20"**,**精排保证"前 20 里最相关的进前 3"**——
  两段各自扬长避短。业界(Dify/RAGFlow/FastGPT/MaxKB)检索链路全是这个结构。

## 3. 代码走读(reranker.py)

```python
# 1. 组装 (query, chunk) 对 —— 交叉编码器的输入形态
pairs = [[query, hit["chunk"]] for hit in hits]

# 2. 逐对打分:输出原始 logits(可正可负,越大越相关)
raw_scores = model.predict(pairs)

# 3. sigmoid 归一化到 0~1 —— 不改变排序,只改数值可读性
probs = 1 / (1 + np.exp(-np.asarray(raw_scores)))

# 4. 按精排分降序取 top_k;保留原双塔分供对照
ranked = sorted(zip(hits, probs), key=lambda x: x[1], reverse=True)
```

**结果同时带两个分**:`score`(双塔余弦)+ `rerank_score`(精排)——
对照它们能直观看到两种模型的"分歧点",这本身就是学习材料。

模型加载与《03》同款:`_resolve_model_path()` 解析本地快照目录直载
(`models--BAAI--bge-reranker-base/snapshots/<hash>/`),彻底离线。

## 4. 实证:一次肉眼可见的排序修正(2026-08-18 验收)

问题:**"Wireshark 里怎么解密 HTTPS 流量?"**

| 名次 | 粗排(双塔)选的 | 精排(交叉编码器)选的 |
|---|---|---|
| #1 | 块153:跟踪TCP流窗口格式(余弦 0.717) | 块153(不变,精排 0.729) |
| #2 | 块148:明文密码分析(余弦 0.701) | 块148(不变,精排 0.723) |
| #3 | 块147:**"非缺省端口"**(余弦 0.700)— 和解密无关 | **块92:"Preferences 对话框配置"**(精排 0.589)— 被从粗排第 8+ 提上来 |

**关键**:块 92 的向量余弦只有 0.626(双塔眼里排名靠后),但 Wireshark 解密 HTTPS
的正确路径恰是 `Edit → Preferences → SSL`——交叉编码器通过词级交互判断出
"Preferences 配置界面"与"解密操作"强相关。**精排捞回的正是答案所在的章节**,
最终 LLM 的回答完整引用了这条路径。

这就是重排序的价值:不产生新知识,但**把对的知识从第 8 名提到第 3 名**,
让它进入 LLM 的视野。

## 6. 业界选型与取舍

### 选型一:Rerank 模型

| 候选 | 特点 | 劣势(对本场景) |
|------|------|------|
| **bge-reranker-base(本项目)** | 中文强、1.1GB 本地离线免费 | 单语种 |
| bge-reranker-v2-m3 | 多语言、效果更强 | 568M 参数,体积×2,慢 |
| Cohere Rerank(API) | 效果强、零本地资源 | 付费 + 数据外发 + 网络延迟 |
| LLM-as-reranker | 把候选塞给大模型打分,理解力最强 | 每次调用贵且慢,token 成本高 |

**本项目的取舍逻辑**:标准 ①本地离线免费 ②中文效果 ③延迟可控(20 对候选秒级内)
④8G 显存放得下。base 档全占,效果在实测中已肉眼可见(见 §4 实证)。
LLM-as-reranker 是趋势但成本不匹配学习项目。

### 选型二:要不要 rerank(而不是选哪个)

单论文本档的 RAG,rerank 是**性价比最高的单项升级**——Dify/RAGFlow/FastGPT/MaxKB
全部内置,本项目实测也验证了排序修正价值。相比之下混合检索解决的是另一类问题
(关键词精确匹配),两者互补不互替。
