# 01 · 文档解析(preprocessor)

> 解决的问题:把 PDF/Markdown 等各种格式的文档,变成**统一的纯文本**,
> 供下游分块。RAG 的第一站:解析质量决定后面一切的上限(垃圾进垃圾出)。

## 1. 核心机制:PDF 有两种,解析策略只有对应两种

PDF 本质是一个"容器"格式,内容怎么来的分两种情况:

| | 文本层 PDF | 光栅化 PDF |
|---|---|---|
| 来源 | Word/LaTeX 直接导出 | HTML 转换、扫描件、截图拼合 |
| 内部结构 | 每页有**字符对象**(带坐标/字体) | 页面只有嵌入图片 + 矢量路径,无字符对象 |
| 提取方式 | 直接读字符对象(快、100%准) | 必须渲染成图片 → OCR 识别 |

`pdfplumber`(基于 pdfminer.six)只能做第一种:它**读取** PDF 里已存在的文本层,
不做任何"识别"。对光栅化 PDF,`extract_text()` 返回空。

### 自适应判断(pdf_parser.py)

```python
MIN_TEXT_LENGTH = 10

def _has_text_content(page) -> bool:
    if len(page.chars) == 0:          # 字符对象都没有 → 光栅化页
        return False
    text = page.extract_text()
    if not text or len(text.strip()) < MIN_TEXT_LENGTH:
        return False                  # 有字符但少于10个 → 伪文本层(如只有页码)
    return True
```

每页独立判断——一本 600 页的书可能 590 页有文本层、10 页是插图页,各自走各自的路。

### OCR 降级路径

```python
def _ocr_page(page) -> str:
    page_img = page.to_image(resolution=150)   # 页面渲染成 150dpi 图片
    pil_img = page_img.original
    ocr = _get_ocr()                            # RapidOCR 单例
    result, _ = ocr(pil_img)                    # [[box, text, score], ...]
    return "\n".join(item[1] for item in result)
```

**要点**:
- `resolution=150` 是速度/质量的平衡点:再低识别率掉,再高(300dpi)慢一倍但收益小
- RapidOCR 返回的是"检测框列表",`item[1]` 是每个框里的文本,按文档阅读顺序拼接
- `_get_ocr()` 单例:OCR 引擎初始化要加载检测+识别两个模型(秒级),
  逐页调用绝不能重复初始化——单例是必须的,不是优化

## 2. RapidOCR 是什么、为什么选它

`rapidocr-onnxruntime` = **PaddleOCR 训练的 PP-OCRv3 模型 + ONNX Runtime 推理引擎**,
不依赖 paddlepaddle 本身。

选它的原因(Windows 环境约束):
- PaddlePaddle 3.x 在 Windows 有 oneDNN 兼容 bug,2.x 依赖链过长(imgaug/scipy 全家桶)
- ONNX Runtime 是独立推理引擎,只需 `onnxruntime` + `opencv-python` 两个依赖
- 识别效果与 PaddleOCR 一致(模型就是 PaddleOCR 训练的)

## 3. 踩坑记录

- **pdfplumber 不做 OCR**(常见误解):装了 pdfplumber ≠ 能读扫描件。OCR 能力来自
  RapidOCR,"哪页走 OCR"的判断是我们自己写的——这个判断逻辑是解析器的灵魂
- `page.to_image()` 需要 ghostscript 渲染支持(渲染,不是识别)

## 4. 业界选型与取舍

### 选型一:OCR / 解析引擎

| 候选 | 路线 | 优势 | 劣势 |
|------|------|------|------|
| PaddleOCR(原生) | 传统 OCR,检测+识别 | 生态最全 | paddlepaddle 3.x 有 Windows oneDNN bug;2.x 依赖链巨长 |
| **RapidOCR(本项目)** | 同源模型 + ONNX 推理 | 模型同源效果一致;依赖极轻;离线免费 | 无版面理解 |
| 云端 OCR API(百度/腾讯) | 传统 OCR 服务化 | 无本地资源占用 | 按量付费;数据外发;依赖网络 |
| Unstructured | 通用解析库 | 开箱支持几十种格式 | 黑盒,学习价值低;中文效果一般 |
| MinerU / DeepDoc | 版面模型混合路线 | **懂版面**(标题/表格/阅读顺序) | 重(带模型);对纯文本书籍收益小 |
| 生成式(Unlimited-OCR 类) | 端到端 VLM 输出结构化 | 效果天花板 | 3B 模型本地跑不动(8G 显存);API 付费 |

**本项目的取舍逻辑**:取舍标准按优先级是 ①Windows 可装可用 ②依赖轻 ③离线免费
④中文识别效果 ⑤学习透明(能看穿机制)。RapidOCR 在 ①②③⑤ 全占,④ 与 PaddleOCR
同源打平。生成式/版面模型效果更强,但本场景(中文文字版技术书)识别本身不是瓶颈,
版面收益小——**先够用,升级触发条件是"表格/复杂版面文档成为主力"**(那时上 MinerU)。

### 选型二:解析路线(文本层提取框架)

pdfplumber(裸写判断逻辑)胜出,标准是**学习透明性**——自适应降级的判断逻辑
(`_has_text_content`)自己写,才能真懂"文本层 vs 光栅化"的本质;Unstructured
把这一切包起来,快但学不到。
