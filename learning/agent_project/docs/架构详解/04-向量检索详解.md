# 04 · 向量检索(retriever:builder 建库 + searcher 粗排)

> 解决的问题:把向量存成**可高效检索**的库(离线);给定问题向量,
> 迅速找出库里**最相似的 k 个**(在线)。本模块是"粗排",配合《05》精排构成两段式。

## 1. FAISS 的哲学:只存向量,只认 id

FAISS(Meta 开源的向量检索库)的核心设定:

- **它只存向量,不存原文、不存元数据**
- 检索时**只返回整数 id**(和分数),"id 对应哪段文字"它一无所知

所以本项目显式维护**双产物**,靠"下标 id"一一对应:

```
data/output/
├── Wireshark3-2018-_97e8d9dd.index   ← FAISS 的:313 个 512 维向量(952KB)
└── Wireshark3-2018-_97e8d9dd.json    ← 我们的:313 段原文 + 元数据(592KB)
                                         {"chunks": [...], "metas": [{"source", "chunk_idx"}]}
```

建库时按顺序 add 向量、按顺序存原文 → **下标即 id**。
检索时 FAISS 吐出 id → 拿 id 回查 JSON → 取回原文。
这个"id → 原文的映射自己做"正是所有向量库内部干的事,裸写才能看穿。

## 2. 建库(builder.py)关键决策

### IndexFlatIP:精确内积索引

```python
index = faiss.IndexFlatIP(EMBED_DIM)   # 512 维
index.add(vecs)
```

- `Flat` = 不做任何压缩/近似,**精确暴力扫描**全库 —— 313 个向量毫秒级,
  语料到几十万块之前都不需要近似索引(IVF/HNSW)
- `IP` = 内积;《03》里向量已 L2 归一化 → **内积 = 余弦相似度**,
  分数语义直观(越大越相似,值域 [-1,1])

### float32 + C 连续内存(FAISS 的 C++ 接口要求)

```python
vecs = np.asarray(embed_texts(chunks), dtype="float32")        # 必须 float32
vecs = np.ascontiguousarray(vecs, dtype="float32")             # 防御性兜底
```

从 Python list 构造的数组**天然 C 连续**(`np.asarray` 直接连续);
只有切片(`arr[:, ::2]`)、转置(`arr.T`)才会破坏连续性。
第二行在当前数据流下是 no-op,但作为"靠近 C 边界"的防御写法保留——
将来上游换了数据处理方式它就兜底了。

### 元数据设计

```python
metas = [{"source": 文件名, "chunk_idx": i} for i in range(len(chunks))]
```
现在看似冗余,将来"按来源过滤""引用定位到第几块"都靠它。

## 3. 检索(searcher.py)

```python
index = faiss.read_index(str(index_path))          # 读向量库
q_vec = np.asarray(embed_query(query), dtype="float32")  # 问题向量(已加BGE前缀)
scores, ids = index.search(q_vec, k)               # → 形状均为 (1, k)
for i, s in zip(ids[0], scores[0]):                # id 回查 JSON
    if 0 <= i < len(chunks):                       # 过滤 FAISS 的 -1 占位
        results.append({"chunk", "meta", "score"})
```

**id = -1 的坑**:k 超过库大小时,FAISS 用 -1 占位补齐形状,必须过滤,
否则 `chunks[-1]` 会"成功"取到倒数第一块——**静默错误**,比崩溃危险。

## 4. 踩坑记录

| 坑 | 现象 | 解法 |
|----|------|------|
| 中文文件名 | `faiss.write_index` 报 "Illegal byte sequence" | Windows 下它走 C 标准库 fopen,不支持非 ASCII;产物名转 ASCII+md5 短哈希(防中文文档撞名),原名存 JSON 的 source 字段可追溯 |
| id=-1 占位 | 见上 | 过滤 `0 <= i < len(chunks)` |

## 5. 业界选型与取舍

### 选型一:FAISS vs 向量数据库 vs 轻量近邻库

| | FAISS(本项目) | 向量数据库(Weaviate/Qdrant/Milvus/pgvector) | hnswlib 等轻量库 |
|---|---|---|---|
| 本质 | 算法库,产物是文件 | 服务,带存储+查询引擎 | 算法库,更轻 |
| 多文档统一检索 | 要自己合并 | 原生(集合+元数据过滤) | 要自己做 |
| 增量更新 | Flat 可 add,文件级管理 | 原生 upsert | 支持 |
| 按 meta 过滤 | 无,后过滤 | 原生 hybrid | 无 |
| 运维 | 零 | 部署/监控 | 零 |
| 学习透明度 | **高(裸写 id 映射)** | 被服务封装 | 高 |

**本项目的取舍逻辑**:当前是单文档、无过滤、无增量、313 个向量——
FAISS 文件级方案在"够用"的同时**学习价值最大**(亲手维护 id→原文映射,
看穿所有向量库的内部本质)。Dify 们用 Weaviate 是因为他们多租户多文档。
**升级触发条件**:多文档统一知识库、元数据过滤、增量更新 → 向量数据库
(pgvector 最省事,一个 Postgres 全包)。

### 选型二:索引类型(IndexFlatIP vs IVF vs HNSW)

Flat = 精确暴力,O(n) 扫全库——**百万级以下它既精确又够快**(313 个向量是毫秒)。
IVF/HNSW 是近似索引(牺牲一点召回换数量级提速),百万到亿级向量才需要。
**取舍逻辑:量级决定索引,不要过早优化。**

## 6. 接口契约

```
build_index(file_path, chunk_size=500, chunk_overlap=50)
    → (index_path, meta_path, 块数)          # 离线,跑一次

search(query, index_path, meta_path, k)
    → [{"chunk", "meta", "score"}, ...]       # 在线,按余弦降序
```

search 的输出在完整链路里是**粗排候选**(k=recall_k=20),交给《05-重排序》精排。

### Q2 · IndexFlatIP 的 IP 是什么?为什么归一化后可以用内积做余弦检索?分数的范围和含义?
**难度: 机制** · 考点: 数学 + 索引类型

> **你的回答**:
> ip是内积，归一化后向量的模是1，所以内积等于向量的余弦，分数的范围是[-1,1]

> [!tip] 批改 · 7/10
> ✅ 内积、模=1→内积=余弦、范围[-1,1] 全部正确。
> ❌ **缺"为什么选 IP 不选 L2"**：归一化后 L2 距离² = 2 - 2cosθ，与余弦等价。但 IP 直接返回余弦值（越大越相似），语义更直观；L2 返回距离（越小越相似），需要脑内转换。
> ❌ **没提 Flat+IP 组合含义**：Flat=精确暴力扫描全库，IP=内积打分——313 个向量毫秒级精确结果，不需要近似索引。
>
> **改进版**：
> IP=内积。归一化后 ||a||=||b||=1，内积 a·b = cos(θ)，值域[-1,1]，越大越相似。为什么用 IP 不用 L2：归一化后 L2² = 2-2cosθ 与余弦等价，但 IP 直接返回余弦值，语义直观。Flat+IP 组合：精确暴力扫描全库——313 个向量毫秒级，百万级以下既精确又够快。

## 8. 扩展:混合检索(SPEC-002,向量 + BM25 + RRF)

纯向量检索(上文)对**专有名词/字面精确匹配**弱——向量只认"语义相近"。
`retriever/hybrid.py` 给粗排加了第二条路:

```
query ──┬── 向量检索 top-N(search,语义泛化强)──┐
        │                                      ├─→ RRF 融合 → top-20 → rerank 精排(不变)
        └── BM25 全文 top-N(jieba分词,字面精确)┘
```

**RRF(倒数排名融合)裸机制**:`score(d) = Σ_各路 1/(k_rrf + rank_i(d))`,k=60。
只用**排名**不用原始分——余弦和 BM25 分数量纲不同,排名才可比;两路都靠前的块
被加分(共识奖励)。纯函数 `_rrf_fuse` 的数学正确性由 `tests/test_rrf.py` 验证
(该测试还揪出了 spec 草稿的手算错误——"测试暴露 spec 错误"的首个案例)。

**BM25 为什么必须分词**:它按"词项重合"打分,中文必须先切词(jieba),
且查询与文档用**同一个**分词器(两边切法不同=各说各话)。

**实证(2026-08-18 验收)**:
- query=`pcapng`:纯向量 top-20 **漏掉全部 10 个字面含该词的块**,混合检索全数捞回
- 语义型查询(无字面重合):原向量 top-5 命中 5/5 保留,2 块还升到前 2 名——互补不回退

### Q&A 补充(混合检索 3 问)

### Q7 · 为什么 RRF 只用排名、不用两路的原始分数直接加权相加?
**难度: 机制** · 考点: 量纲问题

> **你的回答**:
> 不同检索方式的分布是不同的，他们的值在各自范围内的大小不一样，需要找到一个可参考的相对值，排名就是这么一个值

> [!tip] 批改 · 8/10
> ✅ "分布不同、值域不同"正确；"排名是相对值"正确。核心直觉到位。
> ❌ **可以更精确**：举具体例子——余弦值域[-1,1]，BM25 值域[0,+∞)，直接加权等于让一个维度碾压另一个。排名是无量纲的，可比。
> ❌ **缺"共识奖励"机制**：RRF 的 Σ 1/(k+rank) 让两路都靠前的块被加分——这是 RRF 比简单取交集更鲁棒的原因。
>
> **改进版**：
> 余弦值域[-1,1]，BM25 值域[0,+∞)，直接加权等于让一个维度碾压另一个。排名是无量纲的相对值，跨路可比。RRF 用 Σ 1/(k+rank) 融合：两路都靠前的块被加分（共识奖励），只一路靠前的加分少。k=60 是平滑参数，防止第1名和第2名差距过大。

### Q9 · 混合检索和重排序都让检索"更准",它们解决的是同一个问题吗?各自补的是什么短板?

> [!tip] 批改 · 7/10
> ✅ "混合=召回率，重排=准确率"核心判断正确；"增加内容 vs 选择正确"区分好。

>
> **改进版**：
> 混合检索和重排序解决不同问题：混合检索在**粗排阶段**补**召回率**——向量认语义（"加密"→"TLS"），BM25 认字面（"pcapng"→"pcapng"），互补让漏网更少。重排序在**精排阶段**补**准确率**——交叉编码器把 query+chunk 拼一起逐对打分，做双塔做不到的细粒度语义交互，从 20 个候选里选出最相关的 5 个。链路：粗排捞多 → 精排选准。

## 9. 扩展:多文档检索(SPEC-005,2×D 路 RRF + 精排纠序)

知识库从"一本书"扩到"任意多份文档":每文档一对 (.index, .json) 产物
(`python -m agent_project.ingest <文件>` 入库),检索时 `hybrid_search_all()`
对**每个文档**各出"向量一路 + BM25 一路"排名 → **2×D 路 RRF 融合**:

```
doc1 ──┬── 向量 top-n ──┐
       └── BM25 top-n ──┤
doc2 ──┬── 向量 top-n ──┼──→ _rrf_fuse(2×D 路排名)→ top-k → rerank 精排
       └── BM25 top-n ──┤       (候选 key=(doc_id, chunk_idx) 元组)
...                    ┘
```

候选 key 用 `(doc_id, chunk_idx)` **元组**——`_rrf_fuse` 只要求可哈希,原样复用,
这就是当初把融合写成纯函数的红利。跨文档只用排名不用分数,大文档小文档机会均等。

**真机踩坑:小文档名次压缩(SPEC-008 评测量化暴露)**。裸 RRF 下,3 块小文档的
任何块都天然是双路 top-3,弱匹配拿满融合分,把大文档真匹配挤出 top-3 ——
评测基线实测:混合 hit@3 仅 56%,**反低于**纯向量 75%。RRF 假设各路排名分布
可比,小库把排名压扁了,假设被破坏。

**三层修复**(SPEC-005 修订记录,按必要性排序):
1. **全局 BM25(治本)**:rank_bm25 的 IDF 是**库内**统计——各库分别建词法索引时,
   小库 0.09 分的噪音匹配也拿满"第1名",与大库 13.2 分的第1名在 RRF 同权。
   修法:合并全部文档块统一建**全局** BM25(IDF 全局化),弱词法匹配沉到长尾。
   修后:混合 56%→75%,literal 桶 78%→**100%**(vs 纯向量 89%)。
   认知一句话:**向量分数同一嵌入模型天然跨库可比,可分路;BM25 分数不跨库可比,必须全局**
2. **向量路相似度地板(cosine<0.35 不参与排名)**:卫生项,砍掉弱语义匹配的排名资格
3. **下游交叉编码器精排(最终裁判)**:对 (query, chunk) 逐对打分,完全不看名次分布,
   天然免疫融合伪影;agent 的 search 工具因此是两段式(见 07 详解),MRR 0.604→0.688
